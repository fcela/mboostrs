# Building the mboostrs book

The documentation is a [MyST / Jupyter Book](https://jupyterbook.org) with three
parts: usage tutorials (executable), a methodology review, and implementation
details. It renders to a website and to a single PDF.

## Setup

```bash
npm install -g mystmd
pip install -r requirements.txt maturin
maturin develop --release  # or build/install a wheel outside a virtualenv
```

The Part I tutorials execute against the **installed** `mboostrs`. The Python
sources and compiled extension must come from the same build; a version string
alone cannot detect a stale extension after its return contract changes.

## Website (HTML)

```bash
bash build-html.sh  # -> _build/html/index.html
```

For a live preview that executes notebook cells, run `bash start.sh` from
`docs/book`. The script activates the repository `.venv` (or the environment
named by `MBOOSTRS_DOCS_VENV`), checks the installed Python/native build, and
starts MyST. A bare `myst start --execute` needs `python` on the shell's
`PATH`, with `jupyter-server` and `ipykernel` installed in that interpreter;
if `python` is missing, MyST reports
`Could not load Jupyter session manager` for every uncached notebook. To use
the direct command instead, activate the environment first:

```bash
source ../../.venv/bin/activate
myst start --execute
```

`build-html.sh` is the supported local website build. It re-executes the
tutorial cells, regenerates derived figures, and runs
`merge-outputs.py`. That merge step is required because MyST stores notebook
outputs in a separate execute cache; without it, Altair charts can render as
plain reprs such as `alt.VConcatChart(...)` instead of SVG charts.

For a fast HTML-only iteration you can run `myst build --html`, but use the
script before checking visual output or publishing. The script also delegates
the PDF build to `build-pdf.sh` and stages the result under `_build/html/exports/`.
It uses the active Python environment by default; set `MBOOSTRS_DOCS_VENV` to
the directory of a virtual environment if explicit activation is needed.

Both build scripts run a one-iteration native fit before starting MyST. If that
preflight reports a source/native mismatch, rebuild for the exact interpreter
shown in the error (from the repository root):

```bash
maturin build --interpreter /path/to/docs-venv/bin/python --release
/path/to/docs-venv/bin/python -m pip install --force-reinstall \
  target/wheels/<wheel-built-above> --no-deps
```

Using an explicit interpreter matters when the repository also contains a
different `.venv`: `maturin develop` may select that environment instead of the
one used by the documentation kernel.

Before a full render, the same source checks used by CI can be run quickly:

```bash
python check_docs.py
python check_runtime.py
bash execute_examples.sh
```

These reject missing ToC pages, stored notebook exceptions, broken local
links, missing/duplicate page titles, package-version drift, stale generated
capability tables, and failures in any of the eight public example notebooks.

## PDF

```bash
bash build-pdf.sh            # -> exports/mboostrs.pdf
```

The PDF path renders LaTeX, so it needs a TeX installation with the usual book
packages. On a minimal TeX Live you may need, e.g.:

```bash
tlmgr install datetime fmtcount   # packages used by the default book template
```

(Alternatively install the `typst` CLI and set `format: typst` under
`project.exports` in `myst.yml` for a LaTeX-free PDF.)

## Configuration

- `myst.yml` is the canonical configuration (table of contents, math macros,
  bibliography, PDF export).
- `_build/` is generated and git-ignored.
- `book-theme/` contains the versioned local website theme, including its built
  assets. MyST installs its dependencies on first start; `node_modules` is an
  ignored local cache.

## Authoring conventions

- Cross-references use notebook file links (`[](path.ipynb)`); citations use
  `{cite}` against `references.bib`.
- Case studies explain the data, fitting choices, diagnostics and interpretation,
  with one analytical step per code cell. Update examples when a public API
  improvement replaces a workaround.

## Generated content

- **Methodology figures** (Part II) are Altair SVGs generated by
  `generate_figures.py` into `figures/`. Both `build-html.sh` and `build-pdf.sh`
  call this script automatically before the MyST build. To regenerate manually:
  ```bash
  python3 docs/book/generate_figures.py
  ```
- **Capability tables** are generated from the canonical package manifest for
  Python, R, the README, and the book. Regenerate and validate them with:
  ```bash
  python tools/generate_capabilities.py
  python tools/generate_capabilities.py --check
  ```
- **Parity evidence** is produced by `tools/run_parity.py` and validated against
  `docs/schemas/parity-result.schema.json`. CI uploads the node-level JSON ledger
  and its Markdown summary for focused pull-request runs and complete scheduled
  or manually dispatched runs.
- **Benchmark evidence** is declared in `benches/scenarios.json`; results from
  `benches/bench_all.py` are checked against
  `docs/schemas/benchmark-result.schema.json`. Published comparisons must retain
  raw repetitions, provenance, equal timed boundaries, and a shared correctness
  digest.
- **Profile and memory evidence** is measured by `benches/profile_memory.py` in
  fresh processes and checked against
  `docs/schemas/profile-memory-result.schema.json`. It records exclusive stage
  shares, process peak RSS, and retained factor/cross-Gram cache bytes.
